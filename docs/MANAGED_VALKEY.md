# Dedicated Valkey cache

An application can request one private Valkey 9 instance using `POST /v1/organizations/{organization}/applications/{application}/valkey` with an idempotency UUID, `memory_mb` (128–16384) and `cpu_milli` (100–16000). Owners and admins can create; members with viewer access can read `GET` without seeing credentials. The request reserves node resources, records an auditable durable job, and returns `202`. Poll until `READY`. A failed job retains its reservation and volume for operator reconciliation. Idempotent retries with the same request return the existing resource.

The worker creates one app password in OpenBao KV v2 with CAS, delivers the exact revision to the node over mTLS, and starts the selected digest-pinned official `valkey/valkey:9@sha256:…` image. Set `NODE_VALKEY_IMAGE` in the root-only node environment file. The container has a named `/data` volume with append-only persistence, memory/CPU/process limits, an internal resource-specific Docker bridge and **no host port**. The default user is disabled. `dial_app` authenticates with a password and cannot invoke dangerous administrative commands. Node readiness checks AUTH and PING over the private address. The node does not expose credentials in receipts or Docker arguments.

A new application release on the same node gets `CACHE_HOST`, `CACHE_PORT=6379`, `CACHE_USER=dial_app`, and an owner-only host password file mounted read-only as `/run/secrets/valkey_password`; `CACHE_PASSWORD_FILE` points at it. The release joins only its own app bridge and this cache bridge before its health probe. When a cache is created after an active release, submit a new application release to attach it. Cache and PostgreSQL placement must match existing release placement.

Apply `006_valkey.sql` after the earlier control migrations. The bundled Compose profile applies it only when initializing a **new** database. On an existing estate, run the migration with the dedicated migration role before starting the updated API or worker. This code path has disposable CI tests for tenant RLS, job progression, password enforcement, command restrictions, persistence across restart, private network, and release attachment. Qualification on the chosen production estate is still required.

## Off-host backup and restore drill

Install `deploy/node-agent/install-valkey-backup.sh` on a qualified cache node after supplying an owner-only `/etc/dial-hosting/valkey-backup.env` from the example. Configure an encrypted off-host Restic target, initialize it, and retain its password and target credentials separately from the node. Set `NODE_VALKEY_IMAGE` and `NODE_STORAGE_SHELL_IMAGE` to the same immutable digests used by the node agent. The installer enables a daily fleet timer that inventories all labeled Valkey containers and volumes; a missing or mismatched resource causes failure. The backup operator needs Docker access and root-only local temporary space large enough to hold the complete AOF volume archive.

For each resource, place an application-specific, persistent string canary in the cache and create `/etc/dial-hosting/valkey-probes/<resource UUID>.json` as a root-owned 0600 file with `{"key":"backup_canary","sha256":"<64 lowercase hex digits>","size_bytes":123}`. The key allows ASCII letters, digits, colons, underscores and dashes; the value must be nonempty and at most 1 MiB. Keep its expected digest independently from the cache. Because this instance uses `allkeys-lru`, ensure the canary remains present: eviction or expiration makes the backup fail. The job validates a signed/authenticated source read, stops Valkey for a consistent AOF volume snapshot, restarts it in a `finally` block, validates the canary again, uploads to encrypted Restic, restores into a separate volume and internal Docker network, and authenticates to check the restored canary. Only then does it record `RESTORE_VERIFIED`. This causes temporary cache write unavailability; run it in a maintenance window and plan client retry behavior. A failed drill leaves the receipt `BACKUP_CREATED`; retry with `valkey_backup.py verify <resource UUID> <full snapshot ID>` and inspect `systemctl status dial-valkey-backup.service`.

The cache is for reproducible/ephemeral application data. The AOF and off-host restore drill improve recovery but do not provide a production recovery objective or availability guarantee. Do not use Valkey as the sole authoritative store for data that must survive node loss. No public TLS listener, failover cluster, credential rotation, upgrade controller, or self-service delete is present. A node administrator can access Docker networks and volumes.
