# Public release health observations

The deployment worker adds a health row when it promotes a release to `SERVING`. Migration 022 also creates rows for releases that were serving when it was applied. The worker polls only the **current** serving release of an application whose traffic is `ACTIVE`. Each probe verifies that every public A record points to the registered ingress IPv4 address, connects to that address with the hostname's trusted HTTPS certificate, and requires a 2xx response with the exact `X-Dial-Release` header on the release's configured health path.

The worker stores one observation per minute. A successful probe reports `UP`; one or two consecutive failures report `DEGRADED`; three or more report `DOWN`. A transition to `DOWN` emits `release.health_down` in the tenant audit chain and event outbox. A subsequent successful probe emits `release.health_recovered`. A crash or lost lease cannot finalize a stale observation, and a probe finishing after release replacement or traffic suspension is discarded. The next poll is due immediately after traffic resumes.

`GET /v1/organizations/{organization_id}/applications/{application_id}/health` exposes the active release, observation time, consecutive failures, and state to tenant members with release read access. An observation older than three minutes reports `UNKNOWN` even if its last persisted state was `UP` or `DOWN`. `NOT_DEPLOYED` and the traffic transition states are distinct from public probe outcomes. `python3 tools/hosting_cli.py --base-url https://control.example:443 --token-file /private/control.jwt health ORG_ID APP_ID` reads the same data.

Migration 023 retains outage episodes beginning at the third consecutive failure. The tenant `GET .../health/incidents` route and `health-incidents ORG_ID APP_ID` CLI command return the newest 100 episodes with opening and closing times. Recovery closes an episode as `RECOVERED`; a newly promoted release closes the prior release's episode as `SUPERSEDED`; proven owner suspension closes it as `SUSPENDED` and clears the stale probe result. The audit ledger still records down and recovery transitions. An open incident is historical context, not a fresh availability assertion: use the current `/health` observation to determine whether the worker has checked recently.

The read-only `tools/release_health_check.py --max-age-seconds 180 --min-applications N` command checks all active serving applications with restricted `hosting_worker` database credentials. It emits JSON counts and application IDs for missing, stale, degraded, down, and inconsistent states and exits 2 if the estate fails the threshold. Run it from a separately supervised operator scheduler with a known minimum deployment count; otherwise an empty estate can pass. A stale result also catches a stopped or stalled probe worker.

To install minute-by-minute systemd checks on the selected operator monitor, configure `/etc/dial-hosting/release-health-check.env` from `deploy/control/release-health-check.env.example` with a root-owned mode-0600 file and a dedicated restricted `hosting_worker` connection. Set `MIN_ACTIVE_APPLICATIONS` to the known deployment floor and `MAX_AGE_SECONDS` to the alert threshold. Run `sh deploy/control/install-release-health-check.sh` to install the pinned Python runtime and release, node, event outbox, and external public health timers. Supervise failed service results from an independent alert receiver. This installer does not deploy a separate public monitoring location or create the alert receiver.

`dial-external-public-health.service` reads the current active serving release inventory and checks each verified hostname's A records, trusted HTTPS certificate and exact release identity from the operator monitor's network. It exits 2 if an active application fails or the configured application floor is missing, and prints application IDs with bounded failure reasons. Place this monitor on an independently supervised host outside the control worker's network failure domain and allow outbound DNS and HTTPS to public ingress. The check does not change release state; the worker still owns tenant-visible observations and incidents. Its systemd timeout is five minutes for estates whose probes require multiple batches; set an appropriate independent alert for delayed or missing checks.

The tenant-visible probes run from the control worker's network location and share its failure domain. The operator monitor can independently detect public routing failures when installed at another network location, but it does not constitute a multi-region uptime check, application dependency test, status page, or automatic rollback. An operator must arrange host placement, independent incident delivery and live qualification before production use.
