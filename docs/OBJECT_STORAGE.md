# Private application object storage

The owner or admin can queue one dedicated Garage S3 resource per application through `POST /v1/organizations/{org}/applications/{app}/storage`. Send a canonical `idempotency_key` UUID and bounded `memory_mb` and `cpu_milli`; `GET` on the same route reports QUEUED, PROVISIONING, READY or FAILED. The operator CLI has `storage-create` and `storage`. A release can be queued only after an existing resource is READY and on the selected node. The worker reserves node capacity, uses OpenBao KV v2 CAS for exact-revision credentials, requests a typed action over node mTLS and records a durable receipt and audit event.

Set `NODE_GARAGE_IMAGE` on each storage-capable node to the immutable digest of `dxflrs/garage:v2.3.0`, and `NODE_STORAGE_SHELL_IMAGE` to the immutable digest of `busybox:1.37.0-musl`. The node builds a local launcher image from those exact sources because Garage's scratch image has no shell. The shell reads mounted credential files with builtins before executing Garage; no secret is embedded in the launcher image or Docker configuration. The agent launches a single-node Garage instance with a private Docker bridge, no host port, bounded CPU/RAM, persistent volume and an automatically created per-application bucket (`dial-<resource UUID>`). Access and secret keys live in OpenBao and owner-only node revision files; read-only mount copies sit under a node-private directory for the capability-dropped container. Docker receives file paths, not credential values; the application gets its own read-only key files and internal endpoint after the labeled release is attached. The container's bucket key is local to this one instance, so another application's key or network cannot access its objects. The CI runtime test writes and reads signed S3 objects, rejects the other application's key, proves persistence across a container restart, and checks the application-network attachment. This profile exposes no public S3 endpoint.

## Encrypted backup and restore drill

Install `deploy/node-agent/install-storage-backup.sh` as root on a qualified storage node after installing Docker, Python, Restic and supplying `/etc/dial-hosting/storage-backup.env` (root-owned, mode 0600) based on `storage-backup.env.example`. Set `RESTIC_REPOSITORY` to an off-host target, initialize that repository with Restic, keep its password in a separate owner-only file, and provide target credentials through the root-only environment file or the provider's protected credential mechanism. Set `NODE_GARAGE_IMAGE` and `NODE_STORAGE_SHELL_IMAGE` to the same pinned digests used by the node agent. The installer creates root-only evidence, temporary and probe directories and enables a daily randomized systemd timer. This timer is independent of the PostgreSQL backup timer. Its service needs host Docker access; treat it as host privileged.

For **every** storage resource, the operator must first upload a persistent application-specific canary through signed S3 and create `/etc/dial-hosting/storage-probes/<resource UUID>.json` (owner-only, mode 0600). The file is `{"key":"backup-canary","sha256":"<64 lowercase hex digits>","size_bytes":123}`; use the hash and exact nonzero byte size of the canary (at most 1 MiB). Choose a canary whose expected bytes are kept independently of the Garage volume. A missing or changed probe fails the run. `backup-all` inventories labeled containers and volumes and fails closed on a mismatch. For each resource, it checks container isolation and the signed source canary, stops the single-node Garage container, archives the complete volume with an isolated helper, restarts the container even if archive creation fails, checks signed S3 again, then puts the archive in the encrypted off-host Restic repository. This stop incurs brief write unavailability plus archive time; schedule it for a maintenance window and budget local free space at least as large as the volume archive. Write traffic should be held until the restart. The runtime does not coordinate application writes; a client request during the stop may fail.

The same run restores every snapshot into a fresh Docker volume on a new internal network, starts Garage from the pinned launcher and exact credential revision, and checks the canary with signed S3 before recording `RESTORE_VERIFIED`. The source container is never replaced by the drill. Receipts under `BACKUP_EVIDENCE_DIR` begin as `BACKUP_CREATED`; a failed restore leaves them there and causes the service to fail. To retry, run `storage_backup.py verify <resource UUID> <full snapshot ID>` from the installed Python environment. Run `systemctl status dial-storage-backup.service` and inspect protected receipts after each scheduled run; an empty inventory is reported as `FLEET_BACKUP_EMPTY`, not success for a configured resource. Test recovery to a separate node and monitor repository retention, storage growth, backup age, restore time and integrity before qualifying a deployment. Keep an independent copy of the Restic password, repository credentials, probe definitions and Garage credentials for disaster recovery; restoring these files is part of an actual node-loss procedure.

Garage's own single-node guide explicitly says this topology has no data redundancy. This profile therefore remains a development capability. Production requires a selected cluster topology, measured storage placement and quota, recovery objectives, encryption policy, credential rotation, upgrade/repair drill, and client access design. The blueprint's SeaweedFS choice was a research candidate, not a locked release; the Garage choice here is limited to this verified private profile. The project-wide bucket IAM unit and managed Supabase storage are still open. Apply migration `016_object_storage.sql` with the protected migration identity before deploying this API to an existing control database.
