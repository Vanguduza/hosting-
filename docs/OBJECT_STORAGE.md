# Private application object storage

The owner or admin can queue one dedicated Garage S3 resource per application through `POST /v1/organizations/{org}/applications/{app}/storage`. Send a canonical `idempotency_key` UUID and bounded `memory_mb` and `cpu_milli`; `GET` on the same route reports QUEUED, PROVISIONING, READY or FAILED. The operator CLI has `storage-create` and `storage`. A release can be queued only after an existing resource is READY and on the selected node. The worker reserves node capacity, uses OpenBao KV v2 CAS for exact-revision credentials, requests a typed action over node mTLS and records a durable receipt and audit event.

Set `NODE_GARAGE_IMAGE` on each storage-capable node to the immutable digest of `dxflrs/garage:v2.3.0`, and `NODE_STORAGE_SHELL_IMAGE` to the immutable digest of `busybox:1.37.0-musl`. The node builds a local launcher image from those exact sources because Garage's scratch image has no shell. The shell reads mounted credential files with builtins before executing Garage; no secret is embedded in the launcher image or Docker configuration. The agent launches a single-node Garage instance with a private Docker bridge, no host port, bounded CPU/RAM, persistent volume and an automatically created per-application bucket (`dial-<resource UUID>`). Access and secret keys live in OpenBao and node-local owner-only files. Docker receives file paths, not credential values; the application gets its own read-only key files and internal endpoint after the labeled release is attached. The container's bucket key is local to this one instance, so another application's key or network cannot access its objects. The CI runtime test writes and reads signed S3 objects, rejects the other application's key, proves persistence across a container restart, and checks the application-network attachment. This profile exposes no public S3 endpoint.

Garage's own single-node guide explicitly says this topology has no data redundancy. This profile therefore remains a development capability. Production requires a selected cluster topology, measured storage placement and quota, an offsite object-byte backup with semantic restore, encryption policy, credential rotation, upgrade/repair drill, and client access design. The blueprint's SeaweedFS choice was a research candidate, not a locked release; the Garage choice here is limited to this verified private profile. The project-wide bucket IAM unit and managed Supabase storage are still open. Apply migration `016_object_storage.sql` with the protected migration identity before deploying this API to an existing control database.
