# Signed alert receiver and SMTP delivery

The separately deployable `services/alert_receiver.py` accepts the operator monitor's signed alerts at `POST /ingest`. It binds **only** to `127.0.0.1:9143`; place a TLS reverse proxy in front of it and configure the monitor's `ALERT_RECEIVER_URL` with that HTTPS origin. The proxy must pass the three `X-Dial-Alert-*` headers and exact body without modification, set a small request limit, and restrict this route to the monitor where possible. Never expose the loopback HTTP port directly.

The receiver checks HMAC-SHA256 against the raw body, requires a timestamp within five minutes, validates the exact alert shape and ID, and writes the alert into a synchronous private SQLite queue before returning 202. A repeat with the same ID and body also returns 202; a conflicting ID or check sequence is refused. The receiver and monitor use the same signing key and should run in separate failure domains. Rotate the key with a coordinated monitor/receiver change; during a mismatch delivery retries and becomes unhealthy rather than accepting an unauthenticated alert.

The mail timer leases queued alerts, sends a concise message over authenticated SMTP with verified STARTTLS, and retries a transport failure. A recovery for a check waits for its prior failure to be accepted by SMTP. A crash after SMTP accepts an email but before queue acknowledgement can cause a duplicate; each email has a stable Message-ID based on its alert ID. After twelve failed attempts, the alert remains visible and blocks subsequent mail for that check. The hourly queue is inspected each minute; an undelivered message older than five minutes or an exhausted retry fails the health service. Route its failed result to an independent supervisor.

On the receiver host, create root-owned mode-0600 `/etc/dial-alert-receiver/config.json` based on `deploy/alert-receiver/config.json.example` and separate root-owned mode-0600 `signing-key` and `smtp-password` files. The signing key must be 32–4096 bytes and match the monitor key. The SMTP account must be able to send to the configured recipient; test the real server, certificate, credentials, accepted recipient, and receipt from the selected host. Run `sh deploy/alert-receiver/install.sh` to install the loopback receiver and the mail and queue-health timers. The private database lives at `/var/lib/dial-alert-receiver/alerts.sqlite3`.

For its recovery path, initialize a distinct encrypted off-host Restic repository. Create root-owned mode-0600 `/etc/dial-alert-receiver/backup.json` from `deploy/alert-receiver/backup.json.example`, a private `restic-password` file, and an optional backend credential `/etc/dial-alert-receiver/restic.env` from the example. Run `sh deploy/alert-receiver/install-backup.sh` to install daily online SQLite snapshots and isolated restore drills, plus hourly verification of the latest receipt and remote snapshot presence. The SQLite backup API captures one consistent point in time while the receiver can continue accepting alerts. The drill restores into a disposable directory, checks `PRAGMA integrity_check`, and compares the persisted alert ledger digest and archive hash before writing `RESTORE_VERIFIED`. To inspect a snapshot after the source database is lost, use `python3 tools/alert_receiver_backup.py restore --config /etc/dial-alert-receiver/backup.json --snapshot-id FULL_ID` on a recovery host with the receipt directory and Restic repository access. Keep the receiver signing key, SMTP credential, and Restic password in a separately protected recovery set; the alert ledger snapshot does not contain these secrets. A live cross-host drill is still required.

This receiver delivers only operator check failures and recoveries. It does not deliver tenant notifications, SMS, a public status page, or a commercial uptime guarantee. Production qualification requires the selected reverse proxy, independent host, real SMTP and recipient proof, cross-host restore, and external supervision.
