# Off-host audit checkpoints

`tools/audit_checkpoint.py` reads every organization's committed audit events in a consistent PostgreSQL snapshot. It checks each per-tenant hash chain, then records the organization ID, event count, final event ID/hash and a SHA256 digest of every row including its timestamp. It HMAC-signs the document with an owner-protected key and publishes it to a separate encrypted Restic repository with `dial-audit-anchor` and anchor ID tags. A zero-event organization is included. The publisher requires a protected full-tenant database reader with BYPASSRLS or superuser, never the API or worker role.

Create a root-owned mode-0600 JSON config with exactly `version` (1), `anchor_id`, `source_failure_domain`, `recovery_failure_domain`, `repository`, `password_file` and `signing_key_file`. The two named failure domains must differ. The repository must be an explicitly remote Restic URL and initialized with its independent password file. Protect the signing key file and password file with the same owner-only checks; use at least 32 random bytes in the signing key. Supply the protected database connection through `DB_HOST`, `DB_NAME`, `DB_USER` and `DB_PASSWORD_FILE`.

Run `python tools/audit_checkpoint.py --config /etc/dial-hosting/audit-checkpoint.json publish` from a protected operator environment, and record the full snapshot ID outside the source host. Schedule publication and alert if an expected snapshot is absent or stale. Run `python tools/audit_checkpoint.py --config /etc/dial-hosting/audit-checkpoint.json check-latest --max-age-hours 36` under a separately supervised schedule. It selects the newest tagged snapshot, independently restores it, verifies the signature and anchored database history, then checks the signed creation timestamp. It exits 2 for missing or stale evidence; invalid signatures or changed history fail the command. On an independent recovery host with the Restic password, signing key, config and restored database, run `python tools/audit_checkpoint.py --config /etc/dial-hosting/audit-checkpoint.json inspect <full-snapshot-id>`. It restores the selected encrypted snapshot into a temporary directory, verifies the remote tags and HMAC, then compares each anchored chain prefix against the database. Events legitimately appended after the checkpoint are allowed. A missing organization, changed timestamp, missing event or modified hash chain fails inspection.

For a systemd publisher, supply `/etc/dial-hosting/audit-checkpoint.json` and `/etc/dial-hosting/audit-checkpoint.env` as root-owned mode-0600 files. Start from `deploy/control/audit-checkpoint.env.example`; use a protected full-tenant database role, an off-host Restic destination and provider credentials stored outside the repository. Run `sh deploy/control/install-audit-checkpoint.sh` on the chosen publisher. It installs the pinned Python dependencies and source, enables daily publication at 02:15 UTC and an hourly restore, signature, chain and freshness check at minute 45. Supervise both systemd services and route nonzero results to an independent alert receiver. Installation alone does not initialize the remote repository, provision database credentials, enforce object retention or constitute a recovery drill. Run the `inspect` command from the separate recovery host against a selected full snapshot ID as part of the estate drill.

This checkpoint is an external comparison point, not proof of immutable storage. Anyone who can replace the off-host repository and obtain the signing key can forge a new checkpoint. Production qualification requires separately governed key custody, retention or object lock, restore drills on the selected estate, and an alert on publication or inspection failure. The database's own readback endpoint remains described in [tenant audit readback](AUDIT_READBACK.md).
