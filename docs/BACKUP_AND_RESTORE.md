# Control database backup and restore evidence

The control database also has an independent physical PostgreSQL 17 base backup in `tools/control_physical_backup.py`. Configure the protected `deploy/control/control-physical-backup.env.example` as `/etc/dial-hosting/control-physical-backup.env`, using a separate `control-physical-evidence` directory, a digest-pinned official `postgres:17` recovery image, and a replication-capable PostgreSQL administrator. `pg_basebackup -X fetch` streams a tar archive with the WAL required to boot that base backup into encrypted off-host Restic. `backup-and-verify` restores the archive in a disposable internal Docker network and volume, runs PostgreSQL's SHA256 manifest verification, boots the database and checks tenant relationship counts before issuing `RESTORE_VERIFIED`. `deploy/control/install-physical-backup.sh` schedules daily verification and hourly freshness plus remote snapshot checks. Source PostgreSQL must retain WAL throughout the base backup; failure to do so fails the job. This is recovery to the base backup endpoint; continuous WAL archiving and arbitrary point-in-time recovery remain outstanding. Independently test on a separate recovery host before qualifying the estate.

`tools/control_backup.py backup` creates a PostgreSQL custom-format archive, uploads it into an encrypted off-host Restic repository, and writes an owner-only `BACKUP_CREATED` receipt with its archive hash and snapshot ID. It requires `pg_dump`, Restic, private PostgreSQL credentials, and `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE`, `PGHOST`, `PGUSER`, `PGDATABASE`, `PGPASSFILE`, `BACKUP_EVIDENCE_DIR`. Create the Restic repository separately with `restic init` and confirm it is outside the primary host's failure domain. The operator account must be able to read the control DB but not be the public API account.

`tools/control_backup.py verify <full-snapshot-id>` restores the encrypted snapshot to temporary storage, checks the archive hash, creates a randomly named isolated database, runs `pg_restore --exit-on-error`, checks core relationship/count queries, drops the disposable database and only then promotes the receipt to `RESTORE_VERIFIED`. Run the drill on a separate recovery node for failure-domain proof. The receipt is evidence, not a production recovery SLA.

For a daily operator-owned run, configure `/etc/dial-hosting/control-backup.env` from `deploy/control/control-backup.env.example` as root-owned mode 0600, select and initialize an off-host Restic repository, supply owner-only Restic and `.pgpass` files, then run `deploy/control/install-backup.sh` as root on a qualified control backup host. It installs `dial-control-backup.timer`, which executes `backup-and-verify` under a nonblocking lock, plus an hourly freshness timer. The backup identity must have database-wide visibility and permission to create a disposable database for the restore drill. Preserve its credentials and the Restic key outside the primary control host's failure domain; inspect the protected receipt and failed systemd units after each run. The installer does not choose the estate or initialize the repository.

The backup identity must have `BYPASSRLS` or be a protected database administrator so every tenant is included; otherwise `pg_dump` must fail rather than produce a misleading partial archive. Keep its password outside the API and worker environments. This script covers **only the control database**. Separate tools cover client PostgreSQL logical/physical snapshots, Valkey, Garage and OpenBao Raft; see [the recovery catalog](RECOVERY_CATALOG.md) for their per-host inventory and off-host snapshot index. PostgreSQL PITR, registry images, per-project Supabase Auth/Storage and coordinated multi-component checkpoints remain open. Never report a client resource as backed up or restored based on a control-database receipt.

`tools/backup_health.py control <evidence directory>` checks that the newest protected control receipt is `RESTORE_VERIFIED` and no more than 36 hours old. `tools/backup_health.py {postgres,valkey,storage} <evidence directory>` compares live labeled Docker containers and volumes against each resource's newest verified receipt. A missing, stale or unfinished latest snapshot returns a nonzero exit status. Pass `--max-age-hours` to set the age policy or `--min-instances` when an empty node inventory should fail. Resource installers schedule `dial-backup-health@<kind>.timer` hourly with a one-resource minimum: a qualified node with no labeled resource fails rather than reporting an empty inventory as healthy. Scheduled checks also use `restic snapshots --json` to ensure each latest verified snapshot remains present in the configured encrypted repository; `--check-remote` enables that behavior for manual checks. Monitor failed systemd units and route those failures to the site's alerting system. The metadata lookup does not read every data pack, prove a recovery objective or replace a restore on an independent node.
