# Trusted application build and admission

The build node is distinct from every production runtime node. It runs a rootless Docker Engine and a named Buildx `docker-container` builder. Registry credentials and a dedicated Cosign signing key live on the builder only; the runtime agent receives neither. Only DIAL-controlled source is admitted in this profile. Arbitrary external client or untrusted PR code requires a certified stronger isolation class.

`tools/build_release.py` requires a clean checked-out full Git commit, a Dockerfile within that checkout, a registry repository, a named isolated builder, the signing key, the corresponding public key, a **restricted** `HOSTING_ADMISSION_DSN` for role `hosting_admitter`, policy revision, and an owner-only evidence directory. The role can only read and insert artifact admission evidence; it cannot read tenant data, update releases or own schema. The script rejects migration/admin credentials before scanning. It pushes a temporary SHA-tagged image, reads the immutable digest from Buildx metadata, signs that digest, verifies the signature, runs Trivy vulnerability/secret checks, produces a CycloneDX SBOM with Syft, and writes an admission receipt to the control DB. Only the digest is accepted by the release API. A failing signature, scanner, SBOM or database insertion prevents admission.

Create the `hosting_admitter` role through the protected `00_create_api_role.sh` bootstrap and apply migration `008_admission.sql`. On existing control databases, create the role with an independently generated password and apply that migration before switching the builder's connection. Keep its credential on the isolated build host, never on a runtime node. Before running it, qualify and pin the Docker/Buildx, BuildKit, Cosign, Trivy and Syft versions and verify the isolated node's registry, CPU, memory, network and disk budgets. The current repository does not automate PR previews, client code isolation, key rotation, license approval or Harbor provisioning. These remain separate gates; a digest in the admission table alone is not a production release certificate.

Admission evidence files are atomically linked into an owner-only directory before the database row is committed. A repeat of the same digest, commit, policy and key returns the recorded receipt only after checking the local signature, scan and SBOM evidence against their hashes and the database row. A crash after all files were saved but before the DB commit can replay that exact evidence. Missing or changed files fail closed and need operator reconciliation; never delete or rewrite evidence to force a replay.

## Signed GitHub push builds

Apply `009_github_builds.sql` after creating separate `hosting_hook` and `hosting_buildworker` login roles. Supply independent passwords of at least 32 characters. The control Compose profile runs `hosting_api.github_webhook` with the hook role and a private `github_webhook` file. Expose its loopback endpoint `POST /v1/github/push` behind a TLS ingress and configure a GitHub repository webhook with that URL, the exact secret, JSON payloads and the `push` event only. Do not reuse the OIDC API endpoint as a webhook. The receiver verifies `X-Hub-Signature-256` against the raw request body before parsing it; each delivery ID is idempotent. Only an enabled, explicitly registered GitHub repository ID, full name and branch can queue a build. Deleting a branch cannot queue a build.

On a protected operator workstation, run `tools/register_git_source.py` with `HOSTING_MIGRATION_DSN` and all of `--organization-id`, `--application-id`, `--repository-id` (GitHub's numeric repository ID), `--full-name`, `--branch`, `--image-repository`, `--dockerfile`, `--builder`, and `--policy-revision`. First independently verify ownership of the repository and its numeric ID. Registration requires the protected migration/operator identity; no tenant or hook role can register sources. Current registration covers one branch and image repository per application, and one repository/branch pair per registered source.

On the isolated nonroot builder host, install the Python requirements in `services/api/requirements.txt`, Git, a rootless Docker Engine, a `docker-container` Buildx builder, Cosign, Trivy and Syft. Provide registry authentication to that dedicated OS identity. Set `HOSTING_BUILD_DSN` to the restricted `hosting_buildworker` connection and `HOSTING_ADMISSION_DSN` to the independent restricted `hosting_admitter` connection. Set `BUILDER_SIGNING_KEY` and `BUILDER_COSIGN_PUBLIC_KEY` to separate private-mode files owned by the builder identity; set `BUILDER_EVIDENCE_DIR` to a private persistent directory. Run `python tools/github_build_worker.py` as that identity with the repository checked out on the builder host. Keep the process under a service manager with restart on failure. Do not share these credentials, engine socket or caches with runtime nodes or untrusted PR builders.

The worker claims a delivery with a 90 minute lease, checks out the exact push commit, runs the full signed build and admission path, then checks the authoritative admission receipt before recording `ADMITTED`. Failed builds retry up to three times; an expired final lease becomes `FAILED`. Allow only jobs that finish within the lease; qualify time budgets on the intended builder before production use. After applying `010_build_visibility.sql`, members can read the latest 100 tenant-scoped builds through `GET /v1/organizations/{org}/applications/{app}/builds`; an admitted build's `image` digest can be submitted through the existing authenticated releases API by an owner or admin. Apply `011_build_release_ownership.sql` before upgrading the API: it prevents another application's GitHub image from being released under a different application, while retaining explicitly operator-admitted shared artifacts. This flow does not deploy automatically. The disposable CI verifies signed HTTP delivery, replay handling, queue permissions and admission reconciliation, but a live rootless build, registry, webhook ingress and runtime release still require qualification.

For a registered private GitHub repository, create a distinct **read-only** GitHub deploy key bound to its numeric repository ID. On the isolated builder, set `GITHUB_DEPLOY_KEYS_DIR` to an absolute owner-only directory and install that repository's key at `<repository ID>.key`, owned by the nonroot builder identity with mode 0600. Set `GITHUB_KNOWN_HOSTS_FILE` to a builder-owned 0600 file containing GitHub's independently verified SSH host key; compare its fingerprint with GitHub's official published fingerprint before enabling a key. When a matching key exists, the worker clones only `ssh://git@github.com/<registered owner>/<registered repository>.git`, with that key, strict host verification, disabled agent forwarding and no other identities. It also uses that key for any lazy blob fetch during exact-commit checkout. Revoke and replace the deploy key in GitHub and on the builder when rotating; jobs using the old key will fail and retry. The webhook still requires its independently configured signing secret. A registered source with no matching key uses unauthenticated HTTPS for public repositories. The Git subprocess uses a disposable home and clears inherited SSH commands, credential prompts and Git config injection; an unavailable private key cannot silently borrow a builder user's Git identity. Verify private cloning on the selected builder with the actual GitHub installation before qualifying it.
