# Operator alert delivery

The monitor's four scheduled checks run through `tools/operator_alerts.py run`. Their original JSON output and exit code remain visible in the systemd journal. The wrapper stores a state transition in a private, synchronous SQLite queue before it exits. The first healthy observation sets a baseline; the first failure, later recovery, and subsequent failure each create a stable alert ID. A repeated failure does not flood the receiver.

The dispatcher runs every minute, sends the transition to one configured HTTPS receiver with a 10-second timeout and retries on transport or non-2xx failure. A crash after the receiver accepts a message can send the same ID again. The receiver must deduplicate `X-Dial-Alert-Id` durably before side effects and return 2xx only after durable acceptance. For one check, a recovery waits until its earlier failure has been acknowledged. Other checks continue. After twelve attempts, a dead alert blocks later transitions for that check and the queue health service fails. An operator must inspect the receiver, preserve the queue and repair delivery; do not delete the database to clear a failure.

The UTF-8 JSON body contains `id`, `check`, `sequence`, `state` (`UP` or `DOWN`), and Unix `created_at`. The request carries `X-Dial-Alert-Timestamp` and `X-Dial-Alert-Signature: v1=<lowercase hex HMAC-SHA256>`, computed over timestamp bytes, a literal period and the exact body using raw key-file bytes. The receiver must compare signatures in constant time, enforce a short timestamp window, and persist the alert ID. The HTTPS client verifies the server certificate and never follows a redirect. Keep the receiver outside the control worker's failure domain.

Install a root-owned mode-0600 `/etc/dial-hosting/monitor-alert.env` based on `deploy/control/monitor-alert.env.example` and a separate root-owned mode-0600 32–4096-byte random key. Configure a real HTTPS receiver URL with a path. Then run `sh deploy/control/install-release-health-check.sh` on the supervised monitor. The installer creates a root-only `/var/lib/dial-hosting-monitor/alerts.sqlite3` through systemd `StateDirectory`, starts the four check timers, a dispatch timer and an alert queue health timer. Keep an independent supervisor on the monitor and its timer results: a failed host cannot send its own alert. Back up the monitor queue and signing key across failure domains and rehearse a restore before production qualification.

`python3 tools/operator_alerts.py health --max-age 300` returns nonzero when any of the four checks has never reported, an undelivered transition is too old, or an alert has exhausted retries. A missing timer must also be detected by independent service supervision. This mechanism handles the four operator checks only; it is not the tenant notification gateway, a public status page, or a production alert receiver deployment.
